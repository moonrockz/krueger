# CST q56.5 Design

## Scope

Implement `krueger-q56.5` by introducing a dedicated `src/cst` package and migrating parser CST ownership to it.

This phase is **CST-focused**. AST ownership already lives in `src/ast` from `q56.4`.

## Goals

1. Eliminate parser-owned CST type definitions.
2. Replace stringly CST declaration kinds with typed CST node variants.
3. Preserve comment/trivia and source-span fidelity for top-level tooling use cases.
4. Keep parser diagnostics/recovery behavior stable while improving CST structure.

## Non-goals

1. Full-fidelity CST for every Elm grammar production.
2. Pretty-printer or rewriter implementation.
3. Visitor APIs over CST (handled in visitor issues).

## Architecture

- New package: `src/cst`
- Parser package imports and emits `@cst` structures.
- Root package re-exports CST types from `@cst`.
- Parser keeps AST + diagnostics flow unchanged except CST type ownership and node construction.

## CST Modeling Decisions

### Ownership and package boundaries

- `@cst` owns all concrete syntax types.
- `@parser.ParseResult` references `@cst.ModuleCst?`.
- `@parser` no longer defines CST node contracts directly.

### Typed declaration nodes

Replace `CstDecl { kind : String, ... }` with a typed enum.

- `DeclarationCst`
  - `Function(FunctionCst)`
  - `TypeAlias(TypeAliasCst)`
  - `UnionType(UnionTypeCst)`

### Module-level CST shape

- `ModuleCst`
  - `tokens : Array[Token]` (canonical token stream with trivia)
  - `header : ModuleHeaderCst?`
  - `imports : Array[ImportCst]`
  - `declarations : Array[DeclarationCst]`
  - `span : Span?`

### Node fidelity strategy

For each concrete node we preserve:

1. source span
2. exact token slice for that node
3. token trivia as emitted by scanner (comments/newlines/whitespace)

This supports tooling that needs source mapping and comment recovery without introducing a full grammar CST yet.

### Header/import concrete nodes

- `ModuleHeaderCst`
  - `module_name : String?` (raw parsed name from tokens)
  - `exposing : Array[String]`
  - `span : Span`
  - `tokens : Array[Token]`
- `ImportCst`
  - `module_name : String`
  - `exposing : Array[String]?`
  - `span : Span`
  - `tokens : Array[Token]`

### Declaration concrete nodes

- `FunctionCst`
  - `name : String`
  - `args : Array[String]`
  - `span : Span`
  - `tokens : Array[Token]`
- `TypeAliasCst`
  - `name : String`
  - `type_params : Array[String]`
  - `span : Span`
  - `tokens : Array[Token]`
- `UnionTypeCst`
  - `name : String`
  - `type_params : Array[String]`
  - `span : Span`
  - `tokens : Array[Token]`

## Parser migration strategy

1. Keep parser control flow/diagnostics/recovery logic unchanged.
2. Track token slices for module header, imports, and each declaration.
3. Emit typed `@cst.DeclarationCst` nodes instead of string kinds.
4. Keep `ParseResult.cst` semantics unchanged (`Some` for tokenized input, `None` on scan failure).

## Invariants

1. `ModuleCst.tokens` remains the full scanner token stream.
2. Every CST node `tokens` is a contiguous subsequence of `ModuleCst.tokens`.
3. Node `span` bounds match the first/last token span in its `tokens` slice.
4. Comments/doc-comments remain recoverable through token trivia.

## Testing strategy

1. Add `src/cst` package tests for CST type contracts.
2. Update parser tests to assert typed declaration variants and non-empty declaration token slices.
3. Add parser tests for module header/import CST capture.
4. Keep existing parser diagnostics/recovery tests green.
5. Update root export tests for CST package types.

## Success criteria

1. `src/cst` exists and owns CST contracts.
2. `ParseResult.cst` is `@cst.ModuleCst?`.
3. Parser emits typed CST declaration nodes and preserves token/trivia spans.
4. Existing diagnostics behavior remains intact.
